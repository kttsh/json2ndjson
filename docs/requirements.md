## 1. 目的と範囲

DataSpider Servista のスクリプトから呼び出され、REST API のレスポンスとして保存された JSON ファイルを NDJSON（1 行 1 JSON 値）ファイルに変換する非対話型のコマンドラインツールを定義する。
以下、このツールを**変換ツール**と呼ぶ。
リポジトリ名は `json2ndjson`、配布する実行ファイル名は `json2ndjson.exe` とする。

範囲に含めるのは、変換ツールの機能と非機能、DataSpider 側スクリプトが守るべき呼び出し規約、およびテスト観点である。
API からの取得（REST アダプタの設定）や、NDJSON の転送・ロードは範囲外とし、変換ツールと接続する部分だけを規定する。
技術スタックは Go 1.27 に決定した。
選定の経緯と制約は 5.2 節に、実装とビルドに関する取り決めは 12 章に記す。

## 2. 背景と方針決定

### 2.1 純正機能で対応できない理由

DataSpider Servista 5 は 2026 年 2 月 9 日にリリースされ、オンラインヘルプは 5.0.2 まで公開されている。
5 系の主な変更点は、同梱 JRE の Java 8 から Java 21 への刷新、デフォルト文字エンコーディングの UTF-8 統一、Studio for Desktop の同梱終了である。

JSON ファイルを直接読み書きするアダプタは 4.x 時点で存在せず、公式 FAQ もその旨を明記している。
5.0 の公開されている新機能（グローバルプロキシ、Snowflake アダプタ、SAP S/4HANA Cloud、HULFT10 連携、BigQuery 直接投入、REST アダプタの URL エンコード設定）にも JSON ファイルアダプタは含まれない。
既存の JSON 関連機能（HTTP トリガーの JSON⇔XML 変換、REST アダプタのレスポンス JSON→XML 変換、Mapper の JSON からのスキーマ生成）は、いずれも 1 つの JSON ドキュメントを XML の木構造として扱うものであり、NDJSON を書き出す概念を持たない。

公式 FAQ が示す代替策は「HTTP トリガーで JSON を返して REST アダプタで取得する」と「[外部アプリケーション起動] 処理で外部の変換ツールを呼ぶ」の 2 つである。
前者は Mapper で JSON 文字列を文字列連結で組み立てることになり、エスケープ、型の区別、ネスト構造の処理をすべて手作りする必要があるため、汎用性と保守性の点で採用しない。
本書は後者を前提とする。

### 2.2 決定済みの方針

以下は検討を経て決定した事項である。

- **ページごとの変換と追記（方式 A）**：DataSpider が API を 1 ページずつ取得し、1 ページごとに変換ツールを呼んで出力ファイルに追記する。全ページを保存してから一括変換する方式（方式 B）は採らない。
- **page shifting は取得側で防ぐ**：offset ページング中にデータ集合が変わる問題は、変換方式では解決しない。REST GET の条件をキーセット方式（id の昇順並べ替えと `id[gt]=<前ページ最後の id>`）にして防ぐ。変換ツールの重複排除機能は保険として任意機能に留める。
- **300 MB 程度の入力ファイルを通常運用で処理する**：入力サイズに依存しない一定のメモリで動作するよう、ストリーミング処理を必須とする。
- **ランタイムの持ち込みを極力避ける**：追加のランタイムやライブラリのインストールを要求せず、実行ファイルを配置するだけで動作することを目標とする。
- **実装言語は Go 1.27**：標準ライブラリの `encoding/json/jsontext` でストリーミング読み取りと数値の生字句保持を満たせること、サードパーティ依存をほぼゼロにできること、任意の OS から Windows 用実行ファイルをビルドできることを理由に選定した。開発には Claude Code を用いる。

## 3. 用語

- **NDJSON**：改行区切り JSON。1 行に 1 つの JSON 値を置き、値の内部に生の改行を含めない形式。JSON Lines と同義として扱う。
- **レコード**：変換対象の配列の要素 1 つ。NDJSON の 1 行に対応する。
- **ページ**：API が 1 回のレスポンスで返すレコードの集合。Coupa Core API では最大 50 件。
- **JSON Pointer**：RFC 6901 で定義される JSON 内の位置指定記法。ルートは `""`（本書では便宜上 `/` と表記）、`data` キーの値は `/data` と書く。
- **カーソル**：次ページ取得の起点となる値。キーセット方式では前ページ最後のレコードの id。
- **DataSpider 仮想パス**：DataSpider のファイルシステム上のパス（`/data/...`）。OS の物理パスとは別物である。

## 4. システム構成と処理の流れ

変換ツールは DataSpiderServer が稼働する Windows Server 上に配置され、[外部アプリケーション起動] 処理から同期的に呼び出される。
標準入力は使えないため、入出力はすべてファイルと引数で受け渡す。

1 回のスクリプト実行における流れは次のとおりである。

```
[初期化]      出力ファイルを新規作成（または前回分を退避）、カーソル初期値を設定
[ループ開始]
  [REST GET]  条件: order_by=id, dir=asc, id[gt]=<カーソル>, limit=50
              レスポンス設定: データ出力先=ファイル, /data/work/<api>/page.json
  [外部アプリケーション起動]
              json2ndjson.exe --in <page.json の物理パス> --out <出力の物理パス>
                              --path <配列位置> --append --cursor-key /id
              stdout から records と last_id を取得
  [判定]      records が 0、または limit 未満ならループ終了
              それ以外は last_id をカーソルに設定して次ページへ
  [後始末]    変換済みの page.json を削除
[ループ終了]
[ファイル存在確認] → 後続処理（転送、ロード）へ
```

出力ファイルの要素数を DataSpider が直接数える手段はない。
そのため変換ツールの標準出力（件数とカーソル）をループ制御に使う。
この設計により、DataSpider 側は生の JSON を一切解釈しない。

## 5. 前提と制約

### 5.1 実行環境

- OS は Windows Server。DataSpiderServer と同一サーバーで動作する。
- DataSpiderServer は Windows サービスとして起動されている前提とする。サービス起動時は GUI を表示できず、ネットワークドライブのドライブ文字を参照できない（UNC パスは可）。
- 変換ツールを実行するのは DataSpiderServer の起動アカウントである。実行ファイル、入力ファイル、出力先ディレクトリに対してこのアカウントの権限が必要になる。
- DataSpider Servista 5 は内部のデフォルト文字エンコーディングが UTF-8 である。ただし外部プロセスの標準出力を DataSpider が取り込むときの文字コードは未確認である（10 章）。

### 5.2 ランタイムに関する制約

追加インストールを要求しないという方針から、変換ツールは次の条件を満たすものとする。

- 単一の実行ファイル（または実行ファイルと同じディレクトリに置く数個のファイル）を配置するだけで動作する。
- OS に標準で含まれないランタイム（Java、.NET の追加バージョン、Python、Node.js など）のインストールを前提にしない。
- 実行に必要な依存は実行ファイルに同梱するか、静的にリンクする。

この条件で最初に除外した案は次のとおりである。

- DataSpider Servista 5 が同梱する JRE（Java 21）を流用する案は、製品内部のコンポーネントへの依存であり、製品のバージョンアップやサポート範囲の観点で採用しない。
- Windows Server 標準の PowerShell 5.1 と .NET Framework のみで実装する案は、標準ライブラリにストリーミング JSON パーサがなく、300 MB 入力の要件（7.1 節）と両立しないため採用しない。
- jq を配置する案は追加インストールなしで済むが、通常モードは入力全体をメモリに展開するため 300 MB 入力の要件と両立しない。`--stream` モードは要件を満たしうるが、追記時のロールバックやカーソル出力を jq だけで実現するのは困難である。
- Java 25 と GraalVM native-image の組み合わせは要件を満たせるが、Windows 上で C++ ビルドツールと GraalVM の両方を必要とし、実行ファイルも 20 MB を超えるため採用しない。

残った候補（2026 年 8 月時点の最新版）を次の観点で比較した。

| 観点 | Go 1.27 | .NET 10 Native AOT | Rust 1.98 |
|---|---|---|---|
| ストリーミング JSON | 標準ライブラリ `encoding/json/jsontext` | 標準ライブラリ `Utf8JsonReader`（バッファ境界処理は自前） | サードパーティ `serde_json` など |
| 数値の生字句保持（FR-17） | `jsontext.Value` が生バイト列 | `ValueSpan` が生バイト列 | `arbitrary_precision` 有効時 |
| 外部依存 | ファイルロック用の公式拡張のみ | なし | serde 系クレートが必須 |
| 実行ファイル | 3〜5 MB | 10〜15 MB | 1〜2 MB |
| Windows 向けビルド | 任意の OS からクロスコンパイル可 | Windows 上で VS C++ ビルドツールが必要 | Windows 上で MSVC ビルドツールが必要 |
| コンパイル時間 | 数秒 | 数十秒〜1 分 | 30〜120 秒 |
| 長期サポート | 半年ごとに新版、直近 2 版をサポート | LTS（2028 年 11 月まで） | LTS なし、6 週ごとに新版 |

Go 1.27 を選定した。
決め手は、要件の中核であるストリーミング読み取りと生字句保持を標準ライブラリだけで満たせること、サードパーティ依存をほぼゼロにできること、Claude Code の実行環境（Windows 以外を含む）を問わず Windows 用実行ファイルをビルドできることの 3 点である。
.NET 10 は Windows のファイル操作 API が最も充実しているが、ビルドを Windows 上に限定する制約が重い。
Rust は性能とメモリ効率で優るが、本ツールの負荷はディスク I/O で決まるため差が体感できず、依存クレートの監査と保守要員の確保が負担になる。

### 5.3 [外部アプリケーション起動] 処理の仕様による制約

変換ツールの呼び出し規約は、この処理の仕様（4.3 版ヘルプに基づく。5.0.2 ヘルプでの再確認は 10 章）から導かれる。

- 起動コマンドは DataSpiderServer 稼働 OS のローカル絶対パスで指定する。パスに `=` を含めてはならない。
- 起動引数は 1 つずつ個別に登録する形式で、各引数にスクリプト変数を使える。
- 作業ディレクトリを省略すると `$DATASPIDER_HOME/server` になる。
- 標準入力にデータを渡せない。
- シェルのリダイレクトは直接使えない（`cmd.exe /c` を挟めば可能だが、引用符やパスの空白で事故が起きやすい）。
- 「外部アプリケーションが終了するまで待つ」（既定 ON）と「戻り値が 0 ではない場合にはエラーとする」（既定 ON）により、終了コード 0 以外は `LaunchException` としてスクリプトエラーになる。
- 「標準出力・標準エラー出力を取得する」（既定 OFF）を ON にすると、コンポーネント変数 `stdout` と `stderr` に格納される。
- タイムアウトはミリ秒で指定し、0 は無制限。超過すると起動したプロセスは中断される。
- コンポーネント変数として `exitValue`（起動失敗時は -1）、`stdout`、`stderr`、`error_type`、`error_message` などが取得できる。
- PSP（並列ストリーミング処理）では使用できない。

## 6. 機能要件

### 6.1 入力

| ID | 要件 |
|---|---|
| FR-01 | 入力は RFC 8259 に準拠した JSON ファイルとする。文字コードは UTF-8 とし、BOM の有無を問わず受け付ける。 |
| FR-02 | 入力ファイルは `--in` で 1 つ以上指定できる。複数指定時はファイル名の昇順で処理し、出力順序を保証する。 |
| FR-03 | 入力の改行コードは LF と CRLF の混在を許容する。 |
| FR-04 | 入力ファイルは読み取り専用で開き、変更や削除を行わない。 |

### 6.2 変換対象の指定

API レスポンスのトップレベルの形は API によって異なる。
代表的なパターンを次に示す。

| パターン | 例 | トップレベル | `--path` |
|---|---|---|---|
| 素の配列 | Coupa Core API `GET /api/invoices` | `[ {...}, {...} ]` | `/` |
| エンベロープ付き | Coupa Supplier Portal API `GET /api/v1/invoices` | `{ "data": [...], "meta": {...} }` | `/data` |
| 単一オブジェクト | `GET /api/invoices/{id}` | `{ ... }` | `/`（1 行として出力） |
| エラー応答 | `{ "errors": {...} }` | 配列を含まないオブジェクト | 異常終了 |

| ID | 要件 |
|---|---|
| FR-05 | 変換対象の位置を JSON Pointer で `--path` に指定できる。省略時はルートとする。 |
| FR-06 | 指定位置が配列なら、各要素を 1 レコードとして出力する。 |
| FR-07 | 指定位置がオブジェクトなら、そのオブジェクトを 1 レコードとして出力する。 |
| FR-08 | 指定位置が存在しない、または配列でもオブジェクトでもない（文字列、数値、null）場合は、終了コード 5 で異常終了する。 |
| FR-09 | エラー応答の自動判定は行わない。HTTP ステータスによるエラー判定は REST アダプタ側の責務とし、変換ツールは FR-08 で保険的に検出する。 |

### 6.3 出力形式

| ID | 要件 |
|---|---|
| FR-10 | 出力は 1 行 1 レコードのコンパクト形式（整形なし、要素間の空白なし）とする。 |
| FR-11 | レコード内部の改行、タブ、制御文字は JSON のエスケープ（`\n` など）で表現し、生の改行を行内に含めない。 |
| FR-12 | 行の改行コードは `--newline` で LF と CRLF を選択でき、既定は LF とする。 |
| FR-13 | 出力の文字コードは UTF-8、BOM なしとする。 |
| FR-14 | 最終行にも改行を付ける。`--no-trailing-newline` 指定時は付けない。 |
| FR-15 | レコードのネスト構造（オブジェクト内オブジェクト、配列内配列）はそのまま保持する。フラット化は行わない。 |
| FR-16 | 値は一切変換しない。文字列で表現された金額や日時、null、真偽値はそのまま出力する。 |
| FR-17 | 数値は入力の字句をそのまま出力する（`1.0` を `1` に、大きな整数を浮動小数点に、指数表記に変えない）。 |
| FR-18 | 文字列中の Unicode 文字（絵文字、サロゲートペアを含む）は UTF-8 のまま出力し、不必要な `\uXXXX` 化は行わない。 |
| FR-19 | 変換対象が空配列の場合、レコードを出力せず正常終了する。`--append` でなければ 0 バイトの出力ファイルを作成する。 |

### 6.4 出力ファイルの書き込みと追記

| ID | 要件 |
|---|---|
| FR-20 | 出力先は `--out` で OS の絶対パスとして指定する。パスに空白や日本語を含んでもよい。 |
| FR-21 | 新規作成時（`--append` なし）は一時ファイルに書き込み、完了後に出力パスへリネームする。失敗時に中途半端なファイルを残さない。 |
| FR-22 | `--append` 指定時は既存ファイルの末尾に追記する。既存ファイルが存在しなければ新規作成する。 |
| FR-23 | 追記開始前に既存ファイルのサイズを記録し、追記中に失敗した場合はそのサイズまで切り詰めて元の状態に戻す。 |
| FR-24 | 追記前に既存ファイルの末尾が改行で終わっているか確認し、終わっていなければ改行を補ってから追記する。既存ファイルの中身はサイズと末尾 1 バイト以外読まない。 |
| FR-25 | 同じ出力ファイルに対する同時実行を排他する。排他できない場合は終了コード 4 で異常終了する。 |
| FR-26 | `--append` なしで出力ファイルが既に存在する場合の挙動を `--overwrite` で指定する。省略時は終了コード 4 で異常終了する。 |

### 6.5 件数とカーソルの出力

DataSpider がループ制御に使うため、変換ツールは処理結果を標準出力に返す。

| ID | 要件 |
|---|---|
| FR-27 | 正常終了時、標準出力に 1 行だけ `key=value` を空白区切りで並べた文字列を出力する。 |
| FR-28 | 必須の項目は `records`（出力したレコード数）と `files`（処理した入力ファイル数）とする。 |
| FR-29 | `--cursor-key <JSON Pointer>` 指定時は、最後に出力したレコードからその位置の値を取り出し `last_id=<値>` として出力する。レコードが 0 件なら `last_id` は出力しない。 |
| FR-30 | `--cursor-key` で指定した位置が最後のレコードに存在しない場合は終了コード 5 で異常終了する。 |
| FR-31 | 標準出力にはパスやレコードの内容を含めない。値は ASCII の範囲に収める。 |

出力例を次に示す。

```
records=50 files=1 last_id=123456
```

### 6.6 任意機能

以下は既定で無効とし、オプション指定時のみ動作する。
実装の優先度は低く、初版で省略してもよい。

| ID | 要件 |
|---|---|
| FR-32 | `--dedupe-key <JSON Pointer>` 指定時、その位置の値が同一のレコードを 1 回だけ出力する。追記モードでは既存ファイルの内容は対象にしない（同一実行内のみ）。先に現れたレコードを残す。 |
| FR-33 | `--key-hyphen-to-underscore` 指定時、すべての階層のキー名に含まれる `-` を `_` に置換する。受け側がハイフン付きの列名を扱えない場合に用いる。 |
| FR-34 | `--add-field <キー>=<値>` 指定時、各レコードのトップレベルに指定したキーと文字列値を追加する。複数指定できる。既存キーと衝突した場合は終了コード 1 とする。 |

### 6.7 コマンドラインインターフェース

| 引数 | 必須 | 説明 |
|---|---|---|
| `--in <path>` | 必須 | 入力ファイルの絶対パス。複数回指定可。 |
| `--out <path>` | 必須 | 出力ファイルの絶対パス。 |
| `--path <pointer>` | 任意 | 変換対象の JSON Pointer。既定はルート。 |
| `--append` | 任意 | 追記モード。 |
| `--overwrite` | 任意 | 既存の出力ファイルを上書きする。`--append` と排他。 |
| `--newline lf\|crlf` | 任意 | 行の改行コード。既定は `lf`。 |
| `--no-trailing-newline` | 任意 | 最終行の改行を付けない。 |
| `--cursor-key <pointer>` | 任意 | カーソル値を取り出す位置。 |
| `--dedupe-key <pointer>` | 任意 | 重複排除のキー位置。 |
| `--key-hyphen-to-underscore` | 任意 | キー名のハイフンを下線に置換。 |
| `--add-field <k>=<v>` | 任意 | レコードに固定値を追加。複数回指定可。 |
| `--max-record-bytes <n>` | 任意 | 1 レコードの上限バイト数。超過時の挙動は 7.1 節。 |
| `--version` | 任意 | バージョンを表示して終了コード 0 で終了。 |
| `--help` | 任意 | 使い方を表示して終了コード 0 で終了。 |

| ID | 要件 |
|---|---|
| FR-35 | 引数はすべて明示的に渡す。環境変数や設定ファイルによる暗黙の設定を持たない。 |
| FR-36 | 対話的な入力待ちや GUI 表示を行わない。 |
| FR-37 | 未知の引数、必須引数の欠落、排他的な引数の同時指定は終了コード 1 とする。 |

### 6.8 終了コード

| コード | 意味 | DataSpider 側の扱い |
|---|---|---|
| 0 | 正常終了 | 後続処理へ |
| 1 | 引数不正 | 設定ミス。スクリプト修正が必要 |
| 2 | 入力ファイルが存在しない、または読めない | 前工程（REST GET）の失敗を疑う |
| 3 | JSON 構文エラー | レスポンスの内容を確認 |
| 4 | 出力書き込みエラー（権限、ディスク、排他、既存ファイル） | 環境を確認 |
| 5 | `--path` または `--cursor-key` の位置が不正 | API 仕様の変更やエラー応答を疑う |
| 9 | 予期しない内部エラー | ツールの不具合 |

| ID | 要件 |
|---|---|
| FR-38 | 終了コード 3 のとき、標準エラー出力にエラー位置（ファイル名、行、列またはバイトオフセット）を含める。 |
| FR-39 | 異常終了時は出力ファイルを FR-21 または FR-23 の状態に戻してから終了する。 |

### 6.9 標準出力と標準エラー出力

| ID | 要件 |
|---|---|
| FR-40 | 標準出力は 6.5 節の結果行のみに使い、進捗表示やログを出力しない。 |
| FR-41 | 標準エラー出力には人間向けのエラーメッセージを出力する。正常終了時は何も出力しない。 |
| FR-42 | 標準出力と標準エラー出力の文字コードは UTF-8 とし、標準出力の内容は ASCII の範囲に収める（FR-31）。 |

## 7. 非機能要件

### 7.1 性能と資源

| ID | 要件 |
|---|---|
| NFR-01 | 入力をストリーミングで処理し、配列要素を 1 件ずつ読み、書き、破棄する。入力ファイル全体をメモリに展開しない。 |
| NFR-02 | メモリ使用量は入力ファイルサイズに依存せず、最大レコード 1 件分とバッファの合計に収まる。上限の目安は 256 MB とする。 |

## 9. テスト観点

### 9.1 変換の正しさ

- `"`、`\`、改行、タブ、制御文字（U+0000 から U+001F）を含む文字列がエスケープされ、行が壊れないこと。
- 絵文字などサロゲートペアを含む文字列が UTF-8 のまま出力されること。
- 深いネストと配列内配列が保持されること。
- null、真偽値、文字列の金額、ISO 8601 の日時が変換されないこと。
- `1.0`、`1e10`、64 ビットを超える整数、小数点以下 20 桁の数値が入力の字句のまま出力されること。
- 空配列で 0 バイト（`--append` 時は 0 行追記）になり終了コード 0 になること。
- 単一オブジェクトが 1 行になること。
- キー名にハイフン、空白、日本語を含む場合に正しく出力されること。

### 9.2 入力の異常

- 不正な JSON で終了コード 3 になり、位置が標準エラー出力に出ること。
- BOM 付き入力、CRLF 入力が処理できること。
- `--path` の位置が存在しない、文字列である、null であるときに終了コード 5 になること。
- エラー応答（`{"errors": ...}`）を `--path /` で渡したときに終了コード 5 になること。
- 存在しない入力ファイルで終了コード 2 になること。

### 9.3 出力と追記

- 新規作成の途中で失敗したときに出力ファイルが存在しないこと。
- 追記の途中で失敗したときに既存ファイルが元のサイズに戻ること。
- 末尾に改行のない既存ファイルへ追記したときに行が連結されないこと。
- 同一出力ファイルへの同時実行が排他され、後発が終了コード 4 になること。
- 出力先に書き込み権限がないときに終了コード 4 になること。
- 出力の改行が LF であること（Windows で CRLF になっていないこと）。
- 空白と日本語を含むパスで入出力できること。

### 9.4 性能

- 300 MB の入力でメモリ使用量が上限内に収まり、目標時間内に完了すること。
- 1 レコードが `--max-record-bytes` を超えたときの挙動（異常終了、`--skip-oversize` 時は警告とスキップ）。
- タイムアウトによる中断後に、中途半端な行が残らないこと（NFR-07 の復旧）。

### 9.5 DataSpider との結合

- サービス起動の DataSpiderServer から起動できること（GUI や対話待ちで止まらないこと）。
- `stdout` から `records` と `last_id` を取り出してループ制御できること。
- `stderr` の日本語メッセージが DataSpider 側で文字化けしないこと（10 章の確認事項）。
- キーセット方式で全件取得したとき、重複も欠落もないこと（取得中に別セッションでレコードを追加して確認する）。

## 12. 実装とビルドの取り決め（Go 1.27）

本章は 5.2 節の選定結果に基づき、実装、ビルド、配布に関する要件を定める。
個々の設計判断（パッケージ構成、関数の切り方）は実装時に決め、本章では守るべき境界だけを置く。

### 12.1 言語とツールチェーン

| ID | 要件 |
|---|---|
| IMPL-00 | リポジトリ名は `json2ndjson` とする。`go.mod` のモジュールパスは末尾が `json2ndjson` になるよう設定し（例：`github.com/<組織>/json2ndjson`）、`go build` の既定で `json2ndjson.exe` が生成されるようにする。`main` パッケージはリポジトリ直下に置く。 |
| IMPL-01 | Go 1.27 系の最新パッチ版を用いる。`go.mod` の `go` ディレクティブと `toolchain` ディレクティブでバージョンを固定し、ビルド環境の差で結果が変わらないようにする。 |
| IMPL-02 | 標準ライブラリのみで実装する。例外は Windows のファイルロックに用いる `golang.org/x/sys/windows` だけとし、それ以外のサードパーティモジュールは追加しない。追加が必要になった場合は本書を改訂して理由を記録する。 |
| IMPL-03 | `CGO_ENABLED=0` でビルドし、C コンパイラや外部 DLL に依存しない。 |
| IMPL-04 | `gofmt`、`go vet`、`staticcheck` をコミット前に通す。`staticcheck` は開発環境のみのツールであり、配布物には含めない。 |

### 12.2 JSON 処理

| ID | 要件 |
|---|---|
| IMPL-05 | 入力の読み取りには `encoding/json/jsontext` の `Decoder` を用いる。`--path` で指定した位置まで `ReadToken` で辿り、配列の各要素は `ReadValue` で生の `jsontext.Value` として取り出す。`encoding/json`（v1）の `Unmarshal` や `any` への展開は、要素全体をメモリに構築するため用いない。 |
| IMPL-06 | 出力には `jsontext.Encoder` を用い、`jsontext.Value` を `Compact` してから `WriteValue` で書く。`Encoder` のオプションは `Multiline(false)` とし、`EscapeForHTML` と `EscapeForJS` は無効にする（`<` `>` `&` を `\u003c` などに変えない）。 |
| IMPL-07 | `Decoder` と `Encoder` の両方に `AllowInvalidUTF8(true)` と `AllowDuplicateNames(true)` を設定し、入力の値を検証で落とさない（Q-10 の決定で変更しうる）。 |
| IMPL-08 | 数値は `jsontext.Value` の生バイト列をそのまま書き出し、`float64` や `json.Number` への変換を経由しない（FR-17）。 |
| IMPL-09 | JSON Pointer の解釈（`~0`、`~1` のエスケープ解除、配列添字）は RFC 6901 に従って自前で実装する。標準ライブラリに JSON Pointer の実装はない。 |
| IMPL-10 | `--dedupe-key` と `--cursor-key` の値取り出しは、レコードの `jsontext.Value` を `Decoder` で再走査して行う。レコード全体を `any` に展開しない。 |
| IMPL-11 | ネストの深さに上限（既定 512）を設け、超過は終了コード 3 とする（NFR-08）。 |

### 12.3 ファイル操作

| ID | 要件 |
|---|---|
| IMPL-12 | 新規作成時の原子的な置き換えは、出力先と同じディレクトリに一時ファイルを作り `os.Rename` で置き換える（Windows では既存ファイルを上書きする `MoveFileEx` 相当の動作になる）。 |
| IMPL-13 | 追記時の排他は `golang.org/x/sys/windows` の `LockFileEx` を排他モードかつ非ブロッキングで取得し、取得できなければ終了コード 4 とする。ロックは出力ファイル自身に対して取る。 |
| IMPL-14 | 追記時のロールバックは、追記開始前に `Stat` で得たサイズを記録し、失敗時に `File.Truncate` でそのサイズに戻す。強制終了への備えとして、開始前サイズを出力ファイルと同じディレクトリのジャーナルファイル（例：`<出力名>.journal`）に書き、正常終了時に削除する。次回起動時にジャーナルが残っていれば、記録されたサイズに切り詰めてから処理を始める（NFR-07）。 |
| IMPL-15 | 出力は `bufio.Writer` でバッファリングし、正常終了前に `Flush` と `File.Sync` を呼ぶ。 |
| IMPL-16 | Windows 固有のコード（ファイルロック）はビルドタグで分離し、Linux と macOS ではロックを no-op にした実装を置く。これにより JSON 処理と追記ロジックのテストを Windows 以外でも実行できる。ロック自体のテストは Windows 上で行う（9.3 節）。 |
| IMPL-17 | ファイルパスは引数の文字列をそのまま `os` パッケージに渡す。UNC パス（`\\server\share\...`）と 260 文字を超えるパスは Go の `os` パッケージが扱えるため、特別な変換をしない。 |

### 12.4 コマンドライン

| ID | 要件 |
|---|---|
| IMPL-18 | 引数解析は標準ライブラリの `flag` を用い、`--in` のような二重ハイフン形式で受け付ける（`flag` は一重と二重の両方を受理する）。`--in` の複数指定は `flag.Func` で実装する。 |
| IMPL-19 | 終了コードは `os.Exit` を `main` の 1 箇所に集約し、それ以外の場所では error 値に終了コードを持たせて返す。 |
| IMPL-20 | 標準出力への結果行（6.5 節）は `main` の最後で 1 回だけ書く。処理中に標準出力へ書かない（FR-40）。 |

| ID | 要件 |
|---|---|
| BUILD-01 | 配布物は `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=<タグ>" -o json2ndjson.exe .` で生成した単一の exe とする。 |
| BUILD-02 | ビルドはどの OS 上で行ってもよい。ただし配布前の受け入れテスト（9 章）は Windows Server 上で実行する。 |
| BUILD-03 | 配布物には exe、その SHA-256、対応する要件定義書の版とリリースノートを添える（Q-11）。 |
| BUILD-04 | コード署名を行う場合の証明書と手順は Q-08 の結果に従う。 |
| BUILD-05 | 依存モジュール（`golang.org/x/sys`）のバージョンは `go.sum` で固定し、更新は Go 本体の更新と同時に行う。 |

### 12.6 テストの実装方針

| ID | 要件 |
|---|---|
| TEST-01 | 標準の `testing` パッケージを用い、9 章の観点ごとにテーブル駆動テストを書く。テスト名または `t.Run` のサブテスト名に対応する FR、NFR の ID を含め、要件との対応を追えるようにする。 |
| TEST-02 | 9.1 節と 9.2 節のフィクスチャは `testdata/` に小さな JSON ファイルとして置く。300 MB のフィクスチャはリポジトリに含めず、テスト内で生成する（`testing.Short()` でスキップ可能にする）。 |
| TEST-03 | メモリ上限（NFR-02）は `runtime.MemStats` で 300 MB 入力の処理中のピークを測るテストで確認する。 |
| TEST-04 | 9.5 節の DataSpider との結合テストは自動化の対象外とし、手順書とチェックリストを別途用意する。 |

### 12.7 Claude Code での開発

- リポジトリ直下の `CLAUDE.md` から本書を参照させ、変更のたびに関連する FR、NFR、IMPL の ID を挙げて実装させる。
- 「標準ライブラリのみ」（IMPL-02）と「`any` への展開禁止」（IMPL-05）は Claude Code が破りやすい制約なので、`CLAUDE.md` に明記する。
- 開発環境が Windows でない場合は、IMPL-16 の分離によりユニットテストはそのまま実行でき、Windows 用 exe は BUILD-01 でクロスコンパイルする。Windows 固有部分のテストは Windows Server 上の受け入れテストで補う。
