## 1. 目的と範囲

本書は、json2ndjson の非機能要件(NFR-01〜NFR-13)を検証するテストの計画を定める。
機能要件(FR-xx)の検証は既存の単体テストと結合テストが担っており、本書の対象外とする。

検証の中心となる問いは次の二つである。

- 300 MB 級の大容量 JSON ファイルを、メモリを圧迫せず安定して処理できるか(NFR-01〜NFR-05)。
- 同じ出力ファイルへ多重実行された場合や、処理の途中で強制終了された場合でも、出力ファイルが壊れず復旧できるか(NFR-06〜NFR-08、FR-25)。

これに加えて、運用と配置の要件(NFR-09〜NFR-13)の確認手順を定める。

## 2. 対象アプリケーションと非機能に関わる実装機構

json2ndjson は、DataSpider Servista のスクリプトから同期的に呼び出される非対話型 CLI である。
REST API のレスポンスとして保存された JSON ファイルを NDJSON へ変換し、処理結果(件数とカーソル)を標準出力の 1 行で呼び出し元へ返す。
呼び出し元はタイムアウトを設定してこのツールを起動するため、タイムアウトによる強制終了は異常系ではなく通常運用の一部である。

非機能要件の充足は、実装上は次の機構が担っている。
テスト項目はこれらの機構を壊す方向から設計する。

- **ストリーミング変換**:`encoding/json/jsontext` の Decoder で配列要素を 1 件ずつ読み、書き、破棄する。Go 1.27 では jsonv2 が既定で有効のため追加設定は要らない。ネスト深さは自前の上限 512 で打ち切る(NFR-01、NFR-08)
- **書き込みバッファ**:出力は 64 KiB の `bufio.Writer` を経由する。メモリ使用量は最大レコード 1 件分とバッファの合計に漸近する(NFR-02)
- **一時ファイルと rename**:新規作成モードでは出力と同一ディレクトリの一時ファイルへ書き、確定時に rename で置換する。失敗時に出力パスへ中途半端なファイルを残さない(FR-21、NFR-13)
- **ジャーナルによる復旧**:追記モードでは 1 バイト目を書く前に追記開始前のサイズを `<出力名>.journal` へ記録する。強制終了後の次回実行は、残存ジャーナルを読んで開始前サイズへ切り詰めてから処理を始める(NFR-07)
- **OS 排他ロック**:同一出力への同時実行は Windows の `LockFileEx`(即時失敗指定)で検出し、終了コード 4 で停止する(FR-25)。非 Windows のロックは意図的な no-op であり、排他は成立しない

最後の点は本計画の前提を決める。
排他と強制終了復旧の実体検証は Windows 実機でしか成立しないため、テスト環境を「開発機の自動テスト」と「Windows 実機の受け入れテスト」に分けて計画する(6 章)。

## 3. 検証対象の要件と品質特性

観点の漏れを点検するため、各要件をソフトウェア品質モデル ISO/IEC 25010 の品質特性へ対応づける[^iso25010]。
本ツールは非対話・ローカル完結の CLI であるため、同モデルのうち相互作用性(UI)と互換性(相互運用)の特性は対象外とし、セキュリティは「入力を信頼しない」(NFR-08)と「ネットワーク非アクセス」(NFR-12)に限って扱う。

[^iso25010]: ISO/IEC 25010 はソフトウェア製品の品質を性能効率性、信頼性、セキュリティなど 9 つの特性に分類する国際規格。非機能テストの観点表として広く使われている。

| 要件 ID | 概要 | 品質特性(ISO/IEC 25010) | テスト分類 |
|---|---|---|---|
| NFR-01 | ストリーミング処理(入力全体を展開しない) | 性能効率性(資源効率性) | PERF |
| NFR-02 | メモリ上限の目安 256 MB、入力サイズ非依存 | 性能効率性(資源効率性) | PERF |
| NFR-03 | 300 MB 入力を目標時間内に処理 | 性能効率性(時間効率性) | PERF |
| NFR-04 | 1 レコードの上限バイト数と超過時の挙動 | 性能効率性、信頼性 | PERF |
| NFR-05 | `--dedupe-key` のキー集合メモリの文書化 | 性能効率性(資源効率性) | PERF |
| FR-25 | 同一出力への同時実行の排他(終了コード 4) | 信頼性(障害許容性) | CONC |
| NFR-06 | 冪等(再実行で同じ出力) | 信頼性(成熟性) | REL |
| NFR-07 | 強制終了後の次回実行での復旧 | 信頼性(回復性) | REL |
| NFR-08 | 不正な入力でもクラッシュ・無限ループしない | 信頼性、セキュリティ | REL |
| NFR-09 | 実行ファイルのローカル配置、パスに `=` を含めない | 移植性(設置性) | OPS |
| NFR-10 | 自身のログを持たない(stdout/stderr/終了コードに集約) | 運用性 | OPS |
| NFR-11 | `--version` によるバージョン確認 | 運用性 | OPS |
| NFR-12 | ネットワーク非アクセス | セキュリティ | OPS |
| NFR-13 | 作業ディレクトリ非依存、一時ファイルは出力と同一ディレクトリ | 移植性 | OPS |

## 4. 既存テストの現状と本計画で埋める差分

非機能に関わる自動テストは、すでに次の範囲を押さえている。

- **性能と資源**(`perf_test.go`):300 MB 生成入力の処理時間計測と、ヒープピークが 256 MB 以内かつ入力の半分以下であることの検査。入力サイズを 16 MB から 128 MB へ増やしてもピークがほぼ変わらないことの検査。100 MB 級の巨大単一レコードに対する `--max-record-bytes` と `--skip-oversize` の挙動。レコードサイズに対するヒープ増分の倍率検査
- **復旧とロールバック**(`output_test.go`):追記途中の失敗で開始前サイズへ戻ること。ジャーナルが追記の 1 バイト目より前に fsync されること。ジャーナル残存状態(強制終了の模擬)からの復旧。ロック済みファイルへの後発実行が終了コード 4 になること(プロセス内で 2 つのハンドルを使った模擬)
- **ロックの前提**(`lock_test.go`):非 Windows 実装が no-op であることの明示的な固定

一方で、次の差分が残っている。
本計画のテスト項目(5 章)は主にこの差分を埋める。

1. 既存テストはすべて単一プロセス内で完結する(テストヘルパは `run` 関数を直接呼ぶ)。実プロセスを複数同時に起動する多重実行と、実プロセスの強制終了(kill)は未検証である。
2. 排他ロックの実体(`LockFileEx`)は Windows でのみ働くが、開発環境は非 Windows である。FR-25 と NFR-07 の受け入れ判定は Windows 実機でのみ成立する。
3. メモリ検査は Go ランタイムのヒープ(`runtime.ReadMemStats`)を測っており、OS から見たプロセスのメモリ使用量(ワーキングセット)は測っていない[^rss]。
4. ディスク容量の枯渇、ファジング、race detector、`--dedupe-key` の大規模キーでのメモリ実測(NFR-05 が求める文書化の根拠)が未実施である。

[^rss]: `runtime.ReadMemStats` の HeapAlloc は Go が確保したヒープのみを数える。OS のワーキングセットにはランタイムのスタック、GC の余剰、OS バッファが加わるため、ヒープより大きい値になる。NFR-02 の「上限の目安 256 MB」を運用者がタスクマネージャで確認する場面を考えると、両方の値を記録しておく必要がある。

## 5. テスト項目

各項目に一意の ID を付け、対応する要件 ID と実施環境を示す。
「開発機」は非 Windows を含む任意の環境での `go test` を指し、「実機」は Windows 実機での配布ビルド(`scripts/build-windows.sh` が生成する `json2ndjson.exe`)の実行を指す。
既存の自動テストで担保済みの項目は「既存」列に印を付け、二重投資を避ける。

### 5.1 性能と資源(PERF)

| ID | 検証内容 | 要件 | 環境 | 既存 | 合否基準 |
|---|---|---|---|---|---|
| PERF-01 | 300 MB 入力 1 ファイルの処理時間を計測する | NFR-03 | 開発機+実機 | ○(計測のみ) | 初回は実機の実測値を記録して目標時間を確定する。確定後の再実施では目標時間内に完了する |
| PERF-02 | 300 MB 処理中のメモリピークを計測する | NFR-01、NFR-02 | 開発機+実機 | ○(ヒープのみ) | ヒープピークが 256 MB 以内、かつ入力サイズの半分以下。実機ではワーキングセットのピークも記録し、256 MB を大きく超える場合は原因を調査する |

| PERF-04 | 100 MB 級の巨大単一レコードに対する `--max-record-bytes` の挙動を確認する | NFR-04、NFR-08 | 開発機 | ○ | 上限超過は終了コード 5、`--skip-oversize` 指定時は警告してスキップし継続。ヒープ増分がレコードサイズの一定倍率以内 |
| PERF-05 | `--dedupe-key` にキー 100 万件、500 万件を与えたときのメモリピークを実測する | NFR-05 | 開発機 | × | 実測値を記録し、キー件数あたりのメモリ係数と「何件で 256 MB に達するか」の目安を運用文書(README または本書の付録)に記載する。上限内に収まることは合否条件にしない(NFR-05 は文書化を求めている) |
| PERF-06 | 複数入力ファイル(例:3 MB × 100 ファイル)の合計 300 MB を処理する | NFR-03、FR-02 | 開発機 | × | 単一 300 MB ファイルと同程度の時間で完了し、メモリピークがファイル数に比例しない |
| PERF-07 | GB 級の既存出力ファイルへの追記を計測する | NFR-02、FR-22 | 実機 | △(1 GB 疎ファイルの自動テストあり) | 追記の準備時間とメモリが既存ファイルのサイズに依存しない(実装は末尾 1 バイトのみ読む) |

PERF-01 の目標時間は NFR-03 の定義により実機計測で確定する。
確定した値は `docs/requirements.md` の改版に反映し、DataSpider 側のタイムアウトはその 2 倍以上を設定する(DS-09)。

### 5.2 多重実行(CONC)

排他の実体は Windows のロックであるため、CONC の合否判定はすべて実機で行う。
開発機では同種のテストを実行しても排他は成立しない(no-op)ことを、判定の前提として明記する。

| ID | 検証内容 | 要件 | 環境 | 既存 | 合否基準 |
|---|---|---|---|---|---|
| CONC-01 | 同一の `--out` に対して 2 プロセスを同時に起動する | FR-25 | 実機 | △(プロセス内模擬のみ) | 一方は終了コード 0 で完走し、他方は待たずに終了コード 4 で停止する。出力ファイルは成功側の内容として正当な NDJSON である |
| CONC-02 | 同一の `--out` に対して 10 プロセスを同時に起動し、これを 20 回繰り返す | FR-25、NFR-06 | 実機 | × | 各回で終了コード 0 は高々 1 プロセス。残りは全て終了コード 4 で、標準出力は空。全回終了後に一時ファイルとジャーナルの残骸がなく、出力は正当な NDJSON である |
| CONC-03 | 異なる `--out` への並行実行(例:5 プロセス)が互いに干渉しないことを確認する | FR-25 | 実機 | × | 全プロセスが終了コード 0 で、各出力が単独実行時とバイト単位で一致する |
| CONC-04 | 終了コード 4 を受けた呼び出し元が待って再実行する運用を模擬する(先発の完走後に後発をリトライ) | FR-25、NFR-06 | 実機 | × | リトライは成功する(ロックの解放漏れがない)。`--append` でのリトライ結果が期待レコード列と一致する |
| CONC-05 | 同一の入力ファイルを複数プロセスが同時に読む(出力は別ファイル) | FR-04 | 実機 | × | 全プロセスが終了コード 0(入力は読み取り専用で開くため共有できる) |
| CONC-06 | 先発が保持する一時ファイル、ジャーナルを後発が誤って処分しないことを確認する | FR-25、NFR-07 | 実機 | △(プロセス内模擬のみ) | 後発は終了コード 4 で停止し、先発の一時ファイルとジャーナルに触れない |
| CONC-07 | 全自動テストを race detector 付きで実行する | (設計前提の検証) | 開発機 | × | `go test -race ./...` が全て成功する。本体は単一ゴルーチン設計だが、テストコード側の計測用ゴルーチンを含めてデータ競合の報告が 0 件である |

多重起動は「同時」の再現精度が結果を左右する。
実施手順(7 章)では、各プロセスを起動してから合図で一斉に処理を始めるのではなく、OS のプロセス起動をそのまま連射する方式を採る。
ロックの取得は処理の冒頭で行われるため、起動の数ミリ秒のばらつきがあっても競合窓に十分入る。
繰り返し回数(20 回)は、タイミング依存の取りこぼしを減らすための下限であり、1 回でも異常(0 が 2 つ、出力破損、残骸)が出れば不合格とする。

### 5.3 信頼性と復旧(REL)

DataSpider のタイムアウトによる中断はプロセスの強制終了と同型であるため、独立した項目を設けず REL-01、REL-02 で代表させる。

| ID | 検証内容 | 要件 | 環境 | 既存 | 合否基準 |
|---|---|---|---|---|---|
| REL-01 | 追記モードの処理中に実プロセスを強制終了(`taskkill /F`)し、次回実行で復旧することを確認する。終了のタイミングは追記直後、中盤、確定直前の 3 点以上で変える | NFR-07、FR-23 | 実機 | △(ジャーナル残存の模擬のみ) | 強制終了後、出力ファイルに中途半端な行が残っていてもよい。次回実行が冒頭で追記開始前のサイズへ切り詰めてから処理し、最終的な出力が「開始前の内容+今回のレコード」と一致する |
| REL-02 | 新規作成モードの処理中に実プロセスを強制終了する | FR-21 | 実機 | △ | 出力パスにファイルが存在しない。残存した一時ファイルは次回実行が処分し、次回実行は正常に完了する |
| REL-03 | 同一入力での再実行結果を比較する(3 回) | NFR-06 | 開発機+実機 | △(暗黙) | 3 回の出力がバイト単位で一致する(`cmp` / `fc /b`) |
| REL-04 | 出力先ボリュームの容量を枯渇させた状態で実行する(小容量 VHD またはクォータ) | FR-39、NFR-07 | 実機 | × | 新規モードでは出力パスにファイルが残らない。追記モードでは開始前サイズへ復旧して終了コード 4。いずれも stderr に原因が出て、stdout は空 |
| REL-05 | 敵対的な入力(不正 JSON 各種、ネスト深さ 513、単一の巨大文字列)で異常終了することを確認する | NFR-08 | 開発機 | ○ | クラッシュ(panic による終了コード 9)や無限ループを起こさず、規定の終了コード(3 または 5)で報告する |
| REL-06 | Go のネイティブファジングで JSON 入力の全経路を揺さぶる | NFR-08 | 開発機 | × | `testdata/` の正常系と異常系をシードとし、累計 30 分以上の実行で panic(終了コード 9 相当)が 0 件。発見された不具合入力はコーパスとしてリポジトリに保存し、回帰テスト化する |
| REL-07 | 長時間の繰り返し実行(追記でページングを 1000 回模擬)を行う | NFR-06、FR-22 | 実機 | × | 全回が終了コード 0 で、最終出力の行数が期待値と一致し、メモリやハンドルのリークによる劣化がない |

REL-06 のファジング対象は `run` 関数(引数と入力ファイルの内容を入力とする)とする。
ハーネスは入力バイト列を一時ファイルへ書いて `run` を呼び、戻り値が定義済みの終了コード(0〜5)に収まることだけを検査する。
不正入力で終了コード 3 になるのは正しい挙動であり、検出したいのは panic 由来の 9 とハングである[^fuzz]。

[^fuzz]: Go 1.18 以降の標準ツールチェーンはカバレッジ誘導のファジングを内蔵しており、シードの変異で JSON らしい不正入力を効率よく生成する。シードには有効な JSON を与えるのが定石で、パーサの深部まで到達する変異が得られやすい。

## 6. テスト環境

| 環境 | 用途 | 構成 |
|---|---|---|
| 開発機 | PERF(計測の傾向把握と回帰検知)、REL の自動テスト、ファジング、race detector | 任意の OS。Go 1.27 以降。`go test` で実行 |
| Windows 実機 | CONC と REL の受け入れ判定、PERF の目標時間確定、OPS | 配布先と同等の Windows Server。`scripts/build-windows.sh` で生成した `json2ndjson.exe` を使用 |

実機テストは配布ビルドの実行ファイルで行う。
既存の自動テストはテストプロセス内で `run` 関数を直接呼ぶため、プロセスの境界(ロックの所有、強制終了、標準入出力の分離)を跨ぐ挙動は実行ファイルでしか検証できない。

実機の計測値には環境要因が混入しうる。
とくにウイルス対策ソフトのリアルタイムスキャンは、一時ファイルの rename やロック取得に介入して時間の揺れや一時的な共有違反を生む。
計測は対象ディレクトリをスキャン除外した条件と、除外しない(運用実態に近い)条件の両方で 1 回ずつ行い、差が大きい場合は記録に残す。

## 7. 実施方法

### 7.1 開発機での自動テスト

```sh
# 性能テストを含む全テスト(300 MB 級の生成入力を使うため数分かかる)
go test ./...

# 性能テストだけを計測ログ付きで実行
go test -run 'TestPerf' -v ./...

# 短縮実行(性能テストをスキップ)
go test -short ./...

# race detector 付き(CONC-07)
go test -race ./...

# ファジング(REL-06)。対象ハーネスは追加実装する
go test -fuzz FuzzRun -fuzztime 30m .
```

PERF-05(dedupe のメモリ実測)と PERF-06(複数ファイル)、REL-06 のハーネスは未実装であり、本計画の実施に先立って `perf_test.go` と `fuzz_test.go` へ追加する。
追加分も既存の方針(フィクスチャはテスト内で生成し `-short` でスキップ可能、要件 ID をテスト名に含める)に従う。

### 7.2 実機での多重実行(CONC-01、CONC-02)

PowerShell で実行ファイルを連射し、終了コードを集計する。
次は 10 多重を 20 回繰り返す骨子である。

```powershell
$exe = "D:\tools\json2ndjson\json2ndjson.exe"
$in  = "D:\test\large.json"
$out = "D:\test\out.ndjson"

foreach ($round in 1..20) {
    Remove-Item $out -ErrorAction SilentlyContinue
    $procs = 1..10 | ForEach-Object {
        Start-Process -FilePath $exe -PassThru -NoNewWindow `
            -RedirectStandardOutput "D:\test\stdout_$_.txt" `
            -RedirectStandardError  "D:\test\stderr_$_.txt" `
            -ArgumentList "--in", $in, "--out", $out
    }
    $procs | Wait-Process
    $codes = $procs | ForEach-Object { $_.ExitCode }
    $ok = ($codes | Where-Object { $_ -eq 0 }).Count
    "round=$round codes=$($codes -join ',') ok=$ok"
    if ($ok -gt 1) { throw "終了コード 0 が $ok 個ある(排他が破れている)" }
}
```

各回で、成功プロセスの標準出力(結果行)、失敗プロセスの標準エラー出力、出力ファイルの内容、`.tmp` と `.journal` の残骸の有無を確認する。

### 7.3 実機での強制終了(REL-01、REL-02)

追記モードで大きめの入力(処理に数秒かかるサイズ)を与え、起動から一定時間後に `taskkill /F /PID <pid>` で強制終了する。
待ち時間を変えて終了のタイミングを散らし、各回について次を確認する。

1. 強制終了直後:`.journal` が残っていること(追記モードで 1 バイト以上書いた後の場合)。
2. 次回実行:正常に完了し、出力が「開始前の内容+今回のレコード」と一致すること。
3. 次回実行後:`.journal` と `.tmp` が残っていないこと。

### 7.4 計測値の記録

性能の計測は同一条件で 3 回実行し、中央値を採用する。
記録する値は、処理時間、スループット(MiB/s)、ヒープピーク(テストログ)、ワーキングセットのピーク(実機では `Get-Process` の `PeakWorkingSet64`)、および環境情報(CPU、メモリ、ストレージ種別、ウイルス対策の除外有無)とする。

## 8. 合否判定と報告

合否は 5 章の各項目の基準で判定する。
項目単位の判定に加えて、次の全体条件を受け入れの完了条件とする。

- PERF-01 の実測に基づく目標時間が確定し、`docs/requirements.md` と DataSpider 側のタイムアウト設定(目標時間の 2 倍以上)に反映されている。
- PERF-05 の実測に基づく `--dedupe-key` のメモリ係数が文書化されている(NFR-05 の文書化義務)。
- CONC と REL の実機項目がすべて合格している。
- 不合格項目への対処(修正または既知の制約としての文書化)が完了している。

結果は本書と同じ `docs/` 配下に実施報告書として残し、実施日、ビルドのバージョン(`--version` の出力)、環境情報、計測値、判定を記録する。

## 9. リスクと制約

- **非 Windows では排他が成立しない**:ロックの非 Windows 実装は no-op である。Linux などで本ツールを流用する構成は要件の範囲外であり、多重実行の安全性は保証されない。この制約は README にも明記する
- **メモリ計測の二重性**:自動テストのヒープ計測と OS のワーキングセットは一致しない。運用者向けの目安(タスクマネージャで見える値)は実機計測で別途確定する
- **タイミング依存の取りこぼし**:多重実行と強制終了のテストは競合のタイミングに依存する。繰り返し回数を確保しても「全パターンを尽くした」ことにはならないため、既存のプロセス内注入テスト(決定的にタイミングを固定できる)を併走させ、実機テストは実プロセス境界の確認に位置づける
- **dedupe のメモリは非有界**:`--dedupe-key` のキー集合はレコード数に比例して増える。上限を課す実装は要件にないため、対処は実測に基づく文書化とする(NFR-05)
- **環境要因の混入**:ウイルス対策や共有ストレージが計測とロック挙動に影響しうる。条件を記録し、異常時は除外設定を変えて切り分ける
